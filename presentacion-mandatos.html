Proceso 1 · Agente Explore · Solo lectura

🔍 Auditoría de la ruta

Auditar en profundidad el endpoint y entregar un plan aprobable antes de escribir una línea.

POST /api/alerts/refresh

Qué hace

  • Localiza dónde se define y registra la ruta (route → controller → service)
  • Documenta el flujo de la petición: entrada → respuesta
  • Identifica qué depende de que la ruta sea pública
  • Enumera los riesgos de seguridad concretos

Entregables

  • Mapa del flujo (archivos + líneas reales)
  • Lista de consumidores: cron, frontend, tests
  • Lista de riesgos de seguridad
  • Plan paso a paso para los Procesos 2 y 3
⚠️ Regla de oro: no escribe, edita ni borra código. No avanza sin tu aprobación.
Proceso 2 · Agente general-purpose · Implementación

🔐 Autenticación y Autorización

Añadir un guard y validación de token para que solo usuarios válidos usen el endpoint.

Pasos clave

  • Releer el plan aprobado del Proceso 1
  • Crear backend/src/middleware/authGuard.js
  • Sin token / token inválido → HTTP 401
  • Aplicar el guard solo a la ruta objetivo (no global)
  • Documentar JWT_SECRET o ALERTS_API_KEY en .env.example
  • Ejecutar npm test — 0 regresiones

Mecanismo (a confirmar contigo)

  • JWT (Bearer token) vía middleware Express
  • Alternativa mínima: API key en header x-api-key

Definition of Done

  • Token válido → acceso; inválido → 401
  • /api/weather y el cron siguen operando
  • Suite Jest existente sigue en verde
⚠️ No aplicar el guard globalmente sin confirmar impacto · No hardcodear secretos · Los tests de integración son el Proceso 3.
Proceso 3 · Agente claude · Implementación de tests

🧪 Pruebas de Integración

Confirmar el comportamiento de seguridad con tests, sin tocar las pruebas existentes del negocio.

Casos a cubrir

  • a) Sin token → 401
  • b) Token/clave inválido → 401
  • c) Token/clave válido → 200 + respuesta correcta
  • d) (Opcional) /api/weather sigue accesible sin token

Cómo

  • Imitar el estilo de backend/__tests__/
  • Nuevo archivo alertsRefresh.auth.test.js
  • Usar supertest contra la app Express
  • Correr npm test → suite completa en verde
⚠️ No editar ni borrar tests existentes · No cambiar código de producción para "hacer pasar" un test — si algo falla, se reporta.
Proceso 4 · Agente Plan · Solo lectura (diseño)

🚪 Reto: Revocación de tokens — "Sign out all devices"

Diseñar (sin implementar) cómo revocar tokens activamente en todos los dispositivos.

Preguntas a responder

  • ¿Sigue válido un JWT tras cambiar la contraseña? ¿Por qué?
  • ¿Por qué un JWT stateless no se puede invalidar solo antes de expirar?
  • ¿Cómo se implementa la revocación activa en todos los dispositivos?

Estrategias a comparar

  • Denylist de tokens (jti) en PostgreSQL / Redis
  • tokenVersion / passwordChangedAt por usuario
  • Refresh tokens cortos + rotación
💾 Debe encajar con backend/src/db/pool.js (PostgreSQL opcional) y advertir el impacto del modo "sin base de datos". No implementa código.
