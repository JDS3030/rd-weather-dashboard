🔍 Auditoría — qué encontramos

Flujo verificado

  • alerts.js:7 registraba la ruta sin ningún guard
  • Único control: rate limiter global 150 req/15 min (index.js:9)
  • Ruta → controller → alertService.checkAndUpdateAlertStatus()

Quién depende de la ruta

  • Cron 5 min: llama al service directo, no HTTP → no se rompe
  • Frontend: 0 referencias a alerts/refresh
  • Tests: ninguno golpeaba POST /refresh
Riesgos si seguía pública: DoS por refresh forzado, quema de cuota de WeatherAPI (~31 llamadas por refresh), spam de emails SendGrid, contaminación del historial en PostgreSQL y race conditions sobre el estado global. → Conclusión: proteger la ruta es seguro, no rompe nada.

🔐 Autenticación JWT — qué se construyó

Archivos nuevos

  • src/middleware/authGuard.js — valida Authorization: Bearer <token>
  • scripts/generate-token.js — emite tokens firmados de prueba/servicio

Modificados

  • routes/alerts.js:8 → guard solo en /refresh
  • .env.example + CLAUDE.md → documentan JWT_SECRET
  • package.json → dependencia jsonwebtoken

Comportamiento del guard

  • Firma válida + no expirado → pasa (200)
  • Sin header / formato malo → 401
  • Firma inválida / expirado → 401
  • Sin JWT_SECRET → fail-closed (500, nunca deja pasar)
  • No filtra detalles internos de jwt; logs con prefijo [AUTH]
Aplicado solo a /refresh: /weather, /alerts/status y /history siguen públicos. El cron usa el service directo, así que no necesita token.

Proceso 4 · Agente Plan · Solo diseño

🚪 Revocación de tokens — "Sign out all devices"

Las 3 preguntas, resueltas

  • Un JWT sobrevive al cambio de contraseña: el guard solo verifica firma + exp, no re-consulta al usuario
  • Un JWT stateless no se auto-invalida: verificar es una función pura (token, secret) sin estado
  • Revocar de verdad exige añadir estado en el servidor que el guard consulte

Recomendación

  • tokenVersion por usuario en PostgreSQL (+ password_changed_at)
  • "Sign out all devices" = una escritura: token_version + 1 invalida todos los tokens previos
  • El JWT pasa a llevar { sub, role, tv }; el guard compara tv con el valor actual
  • Descarta Redis (rompería el modo "DB opcional"); sin DB la revocación se deshabilita de forma consciente
Es solo diseño: no se implementó código. Encaja con db/pool.js (isEnabled()/query()) reutilizando el patrón de alert_history. Trade-off: +1 lectura a DB por request protegida (despreciable a este volumen).
